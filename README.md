# AWS-Multi-VPC-Peering-Architecture
The objective of this engineering implementation was to design, construct, validate, and decommission a production-grade multi-VPC cloud networking infrastructure within the AWS Sydney region (ap-southeast-2). The primary architectural goal was to enable bi-directional, high-throughput, and private inter-workload communication between isolated application tiers without exposing the backend compute nodes to the public internet.
To eliminate internet-facing attack vectors, backend compute instances (ewb-app-a and ewb-app-b) reside within isolated private subnets lacking Internet Gateways or auto-assigned public IP addresses. Secure administrative ingress is achieved via a dedicated public-facing Bastion host (ewb-bastion) located in VPC A. Network operators traverse this perimeter using OpenSSH ProxyJump encapsulation over Port 22, ensuring that cryptographic private keys remain strictly on the local administration client and are never loaded onto intermediate cloud jump boxes.
Architecture Topology Breakdown
    • VPC A (CIDR: 10.10.0.0/16): Dual-tier networking containing a Public Subnet (10.10.1.0/24) with an Internet Gateway (ewb-igw-a) attachment for Bastion ingress, and an isolated Private Subnet (10.10.2.0/24) hosting workload ewb-app-a.
    • VPC B (CIDR: 10.20.0.0/16): Single-tier workload network containing an isolated Private Subnet (10.20.1.0/24) hosting workload ewb-app-b. It possesses zero Internet Gateways and no direct public ingress/egress path.
    • Inter-VPC Interconnect: AWS VPC Peering Connection (pcx-0aaa730b936da8d87) establishing private, hardware-accelerated routing across the AWS global network backbone, maintaining sub-millisecond round-trip packet delivery.
